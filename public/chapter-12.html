CHAPTER 12: MOBILE DEVICES SECURITY MODELS

SECTION 1: GOOGLE ANDROID SECURITY

🔑 GOOGLE ANDROID SECURITY (THE BASICS)

Definition: Android is built on the Linux kernel with a layered security architecture.

Key Points:

  • Apps execute using Android Runtime (ART), normally in separate Linux processes.
  • Each app generally has a distinct Linux UID and application sandbox.
  • SELinux (mandatory access control) and app permissions add protection.
  • Sideloading expands distribution choices but increases source-verification responsibilities.

🔑 THE ANDROID SANDBOX (HOW IT WORKS)

Definition: Each app receives a unique Linux UID and isolated private storage.

The Defense-in-Depth Layers (Diagram):

┌─────────────────────────────────────────────────────────────┐
│ Applications (App A | App B | App C)                        │
├─────────────────────────────────────────────────────────────┤
│ Android Runtime (ART + framework APIs)                      │
├─────────────────────────────────────────────────────────────┤
│ Linux Kernel (UIDs + SELinux + isolation)                   │
├─────────────────────────────────────────────────────────────┤
│ Additional controls (Permissions • Verified Boot •          │
│ Hardware-backed Keystore)                                   │
└─────────────────────────────────────────────────────────────┘

Key Points:

  • Linux process isolation, SELinux policies, and permissions restrict access.
  • Apps share information through controlled mechanisms: Content Providers and Intents.
  • Limitation: Sandboxing limits compromise impact but does not eliminate vulnerabilities or user-approved data access.

Walkthrough (Camera Access Example):

  1. App executes under ART.
  1. API checks enforce runtime permission.
  1. Linux UIDs isolate files.
  1. SELinux constrains process capabilities.

Memory Aid:

"UID, SELinux, Intents — Defense in Depth means bypassing one check shouldn't bypass all."

🔑 FILE-SYSTEM PERMISSIONS

Definition: Permissions are how the Linux file system ensures one user cannot access files of other users (or in Android, one app cannot access another).

Key Points:

  • Each application runs as a user with its own set of permissions.
  • Unless a developer explicitly grants permission to expose files, files created by one app cannot be read by another.

🔑 ROOTING AND UNLOCKING DEVICES

Definition: Rooting grants privileged access and can undermine application isolation.

Key Points:

  • Root Permissions (superuser): Unrestricted access to the OS, kernel, and any application.
  • In the Android security model, only the lowest layer (OS kernel) and a small subset of core apps run with root permissions.
  • Rooting a device gives someone privileged root permissions to override Android OS security and do anything on the device.
  • Risk: Changing permissions of an application to root significantly increases the device's vulnerability to malware.

🔑 ANDROID PERMISSION MODEL

Definition: App sandboxing and API permissions enforce complementary controls.

Key Points:

  • Sensitive permissions (camera, microphone, location) may require runtime consent.
  • Users can revoke permissions; some support one-time access.
  • Unused-app permission auto-reset and background-access limits reduce exposure.
  • Risk: Granting an unnecessary permission can still expose data despite sandboxing.
  • Vulnerable Features: "Always on Listening" and "Auto Content Update" can be misused (dynamically enable/disable features, provide location, or record conversations).

⚠️ CASE STUDY: EXCESSIVE MOBILE PERMISSIONS

Scenario: A QR scanner requests camera, contacts, SMS, and microphone access.

Legitimate CapabilityPotential Warning Signs
Camera access to scan QR codes.Contacts, SMS, Microphone without clear purpose.

Discussion: Does sandboxing prevent abuse of user-approved permissions? (Answer: No, it only restricts what the app can do outside of those permissions).

SECTION 2: APPLE iOS SECURITY

🔑 APPLE iOS SECURITY (THE BASICS)

Definition: Apple combines code signing, app review, sandboxing, entitlements, and privacy permissions.

Key Points:

  • App Store is a major distribution channel, with region and policy-dependent alternatives.
  • App review and developer identification reduce risk but cannot guarantee safety.
  • Secure boot and hardware-backed protections help establish device integrity.

🔑 APPLICATION PROVENANCE

Definition: Code signing links executable code to a signing identity and detects unauthorized changes.

Key Points:

  • App review and distribution policies add screening but do not guarantee malware-free apps.
  • Compromised developer accounts and malicious behavior remain possible risks.
  • Signing does not make applications impossible to exploit or modify on compromised devices.
  • App provenance works alongside sandboxing, permissions, and runtime defenses.

🔑 iOS SANDBOX

Definition: Apple isolates applications by running each one in its own sandbox.

Key Points:

  • A sandbox isolates an application's data, resources, and services from other applications.
  • Third-party apps run within restrictive application sandboxes.
  • Entitlements govern access to specific platform capabilities and services.
  • Privacy permissions protect sensitive resources (camera, contacts, location).
  • Apps do not receive unrestricted access to system resources or root privileges.
  • Controlled APIs and extensions support limited sharing between apps.

⚠️ SECURITY CONCERNS OF iOS

Key Points:

  • Browser and app vulnerabilities can still be exploited despite sandboxing.
  • Phishing, malicious links, account takeover, and unsafe configurations remain risks.
  • A compromised or jailbroken device can weaken platform isolation.
  • App review and signing are preventive layers, not guarantees against compromise.
  • Prompt updates, strong authentication, and minimal permissions reduce exposure.

🔑 iOS PRIVACY PERMISSIONS

Definition: The iOS version of permission-based access control, built on a much more limited restriction list than Android.

Key Points:

  • iOS prompts for access to sensitive data depending on the API (location, camera, microphone, photos, contacts, Bluetooth, tracking).
  • Location choices may include: one-time, while-using, or other context-specific access.
  • Users can review and revoke permissions in Settings.
  • Notification authorization is distinct from permission to access private data.

🔑 iOS DATA PROTECTION AND JAILBREAKING

Definition: iOS uses hardware-backed encryption and per-file Data Protection classes.

Key Points:

  • Passcode-associated key protection makes physical possession alone insufficient to read protected data.
  • Data availability depends on the protection class and device lock state.
  • Jailbreaking bypasses platform restrictions and can weaken security controls.
  • Secure Enclave and secure boot support key protection and system integrity.

🔑 ENCRYPTION AND JAILBREAKING iOS

Encryption:

  • Apple relies on application provenance, isolation, and strong access control, plus full-device encryption.
  • Apple's full encryption requires a key on the device (data readable if someone has physical access).
  • Layered approach: Certain data (email, personal data) gets double encryption (only the master passkey can read it).

Jailbreaking:

  • iOS security measures are restrictive and robustly enforced by Apple.
  • Jailbreaking frees the device to download applications from any source.
  • Jailbreaking gives the owner root privileges.
SECTION 3: ANDROID vs. iOS EVOLUTION & COMPARISON

🔑 iOS AND ANDROID EVOLUTION — I (SANDBOX DIFFERENCES)

Definition: Both use sandboxes to isolate apps, but the techniques are quite different.

PlatformHow the Sandbox Works
AndroidEach app runs as a specific "user" with its own UID. The Linux kernel guarantees different "users" are isolated and cannot interfere with each other.
iOSAll apps run as the same user ("mobile"). This means each app is rooted, which gives it access to only its own specific part of the filesystem.

🔑 iOS AND ANDROID EVOLUTION — II (GRANULAR PERMISSIONS)

Definition: Isolation as a means of limiting what apps can do is only one side of the sandboxing issue. This is because not every application is an island and there will often be a requirement for apps to securely and safely access things like APIs, contacts, location, and so forth. (Added exact phrasing from slide).

Key Points:

  • To achieve these secure access requirements, both Android and iOS use granular app permissions that are introduced and refined over time.

AspectAndroidiOS

DistributionFlexible app distribution (sideloading).Controlled code signing, App Store review.
Shared FeaturesHardware-backed keys, secure boot, storage encryption.Hardware-backed keys, secure boot, storage encryption.

Security Outcomes: Depend on updates, configuration, apps, and user behavior. (Added detail)

Secure Sharing Between Applications:

  • Apps need controlled communication, not unrestricted cross-app access.
  • Android: Uses intents, content providers, and permission checks.
  • iOS: Uses extensions, entitlements, and platform-approved sharing APIs.
  • Validate data and enforce authorization at every sharing boundary.
  • Crucial Distinction: iOS apps are not "rooted" simply because they share a Unix account.

Memory Aid:

"Android = Different UIDs. iOS = Same User ('mobile'), but Sandboxed."
SECTION 4: CROSS-DEVICE CONTINUITY (HANDOFF)

🔑 HANDOFF-TYPE FEATURES

Definition: Handoff (introduced in 2014) allows users to move seamlessly between devices, continuing right where they left off.

Examples of Features:

  • Nearby Share & Quick Share
  • Call & Text Continuity
  • Chrome Browser Sync
  • Clipboard Sharing
  • App Continuity

How It Works:

  • Each device must be connected to the same Wi-Fi network and signed into iCloud with the same Apple ID.
  • When connected to the same local ad hoc wireless network, Handoff allows a user to make calls from a Mac or an iPad.

⚠️ THREATS TO HANDOFF (THE 7 RISKS)

RiskDescription
1. Unauthorized Device AccessA nearby unauthorized device could spoof a legitimate device and intercept data, or gain access if authentication is weak.
2. Weak or Insecure PairingRelies on BLE or Wi-Fi Direct. If protocols lack encryption or key exchange, attackers can perform MITM or eavesdropping.
3. Data Leakage Across DevicesClipboard, messages, or app states shared between devices on the same account. A compromised/lost device exposes it all.
4. Account-Based VulnerabilitiesRelies on cloud sync (Apple ID, Google, Samsung). Leaked credentials or hijacked session tokens give access to all linked devices.
5. Insecure Application ContinuityApps may not properly secure handoff tokens/session info. Attackers could resume someone else's session on their own device.
6. Privacy ExposureFeatures like Nearby Share or Bluetooth periodically broadcast device info (name, ID, capabilities) for tracking/profiling.
7. Lack of User AwarenessUsers leave continuity enabled without realizing data auto-syncs. Shared devices (family tablets) might access private sessions.

Memory Aid:

"Access, Pairing, Leakage, Account, Continuity, Privacy, Awareness."

🔑 SECURITY RECOMMENDATIONS FOR HANDOFF

The 8 Recommendations:

  1. Keep OS, apps, and device firmware updated.
  1. Require strong account authentication and review trusted devices.
  1. Use encrypted authenticated protocols and secure pairing.
  1. Limit unnecessary synchronization and visibility on shared devices.
  1. Require explicit user consent for every new device connection.
  1. Allow users to view and manage connected devices.
  1. Disable Handoff on public or untrusted networks.
  1. Revoke access promptly when a device is lost or compromised.
SECTION 5: BYOD & ENTERPRISE MOBILITY MANAGEMENT

🔑 BYOD AND SECURITY

Definition: Bring Your Own Device (BYOD) allows employees to use their own smartphones for business email/access.

Key Points:

  • Risk: BYOD increases data leakage (thousands of uncontrolled devices hold company data).
  • BYOA: Bring Your Own Applications (a variant that compounding the problem).
  • Solution: IT must implement a system to provide, manage, and remotely deploy security policies to each device.
  • MDM (Mobile Device Management): The system IT uses to provide, configure, and manage mobile devices.
  • MAM (Mobile Application Management): Manages application software on mobile devices.

🔑 SECURITY USING ENTERPRISE MOBILITY MANAGEMENT (EMM)

Definition: A framework consisting of sets of people, processes, and technologies required to manage mobile IT within the enterprise.

Key Points:

  • Wide scope: includes security, application management, and financial management.
  • Challenge: System admins lack access to devices, OS/device diversity makes configuring apps on BYOD problematic.
  • Solution: EMM solutions typically deploy middleware MDM to automate management of a wide range of devices.
  • Goal: Automate securing and managing mobile devices due to BYOD.

🔑 MOBILE DEVICE MANAGEMENT (MDM)

Definition: Typically built on a client-server model where the MDM server controls the client agent on the mobile device.

Key Points:

  • Most useful feature: Automatically configuring a registered device with a security template over the air.
  • Process:
    1. Place device into a secure quarantine zone as it joins.
    1. MDM interrogates the device agent to retrieve settings.
    1. Compares settings to the security template.
    1. Automatically downloads the latest security template, switching features on/off.
  • Keeps all registered phones/tablets up to date with the latest security policy automatically.

MDM Tasks:

  • Inventory management
  • Device provisioning
  • Software distribution
  • Security device management
  • Data protection
  • Remote technical support

Memory Aid:

"MDM = Manage the Device."

🔑 MOBILE APPLICATION MANAGEMENT (MAM)

Definition: The main difference between MDM and MAM is that MDM handles device activation/enrollment/provisioning, whereas MAM assists in delivering software.

Key Points:

  • MDM authenticates the user and inventories devices, then hands control to MAM.
  • MAM verifies presence of mandatory applications and optional apps.
  • MAM provides distribution platform for apps with lifecycle management (licensing, configuration, usage tracking).
  • Crucial Role for iOS/Windows Phone: Both are closed systems emphasizing application provenance. MAM uses the vendor's enterprise developer certificate to sign applications.

Memory Aid:

"MAM = Manage the Apps."

"EMM = The Umbrella (People + Processes + Tech)."

✅ THE CORE TRUTH
Android and iOS use fundamentally different sandbox architectures (different UIDs vs. same user "mobile"), but both rely on defense-in-depth: permissions, encryption, and hardware-backed keys. Features like Handoff create seamless convenience but also introduce attack vectors (pairing, leakage, account hijacking). For enterprises, BYOD is inevitable, so mitigating the risk requires a layered management approach: MDM for the device, MAM for the apps, and EMM for the overall framework.
